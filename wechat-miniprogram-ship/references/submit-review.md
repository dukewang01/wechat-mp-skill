# 提审全流程 · 测试账号 · 被驳对策

---

## 一、提审页面有哪些字段

打开「版本管理 → 开发版本 → 提交审核」，通常有这些：

| 字段 | 必填 | 说明 |
|---|---|---|
| 版本描述 | ✅ | ≤200 字，页面要求「列点简要描述功能点」 |
| 图片预览 | 选填 | ≤10 张，jpg/jpeg/bmp/gif/png，每张 ≤5M |
| 视频预览 | 选填 | ≤1 个，mp4，≤20M |
| **测试账号** | 视情况 | 有账号体系**必须**提供 |
| 小程序订单中心 path | 视情况 | **仅交易类需要**，非交易类留空 |
| 审核加急 | 选填 | 有免费额度时可用于快速拿结果 |
| **用户隐私保护指引** | ✅ | **填错必驳**，见 [privacy-and-categories.md](privacy-and-categories.md) |

**页面提示「所填信息只用于审核，不会展示给用户」** —— 所以写得**具体、可核验**就好，不用宣传语气。

## 二、测试账号

### 2.1 官方要求

> 常见拒绝情形 3.3.4：若小程序中存在账号体系，需提供测试号，**包含账号和密码**（可以体验所有功能）。

### 2.2 ★ 首次被打回可能是机制，不是故障

> 当小程序需要开发者提供测试账号才能完成审核体验时，
> 小程序在**首次提交审核时将被打回，再次提交审核时将开放提供测试账号的入口**。

**但有些版本的提审页直接给了填写入口** —— 那就一步到位，不用等打回。

**→ 收到"未提供测试账号"的驳回时，不用改代码，重提并填账号即可。**

### 2.3 测试账号必须是真账号

**绝不要**做「审核员看到 A、用户看到 B」：

| 规范 | 原文 |
|---|---|
| 运营规范 5.19.2 | 禁止「利用技术手段规避平台审核监管：包括但不限于截屏对抗、IP对抗、地域对抗、**人群对抗**等手段」 |
| 运营规范 5.19 | 禁止「**对不同用户群体展示不同服务类目下的内容**」 |

**做法**：测试账号走与真实用户**完全相同**的注册流程。

**这也是设计上的自律**：如果必须为审核员开"后门"，说明产品本身对真实用户有隐瞒。

### 2.4 测试账号怎么选

- **手机号**：用**公开示例号段**（如 `13800080000` 这类），别用可能打通的真实号码
- **密码/PIN**：用简单固定的（如 `123456`），并在备注里写清规则
- **务必注明：手机号只在本机校验、不上传、不发短信** —— 否则审核员会犹豫要不要填

## 三、版本描述怎么写

### 原则

1. **列点**，每条一个功能点（页面明确要求"列点"）
2. **只写实际功能**，不夸大
3. **≤200 字**
4. 如果测试账号规则不显然，**在描述末尾补一句登录方式**

### 模板

```
本次为首次提交。
1. <第一个功能点，一句话说清输入和输出>
2. <第二个功能点>
3. <第三个功能点>
4. <判定边界：只做什么、不做什么>
5. <数据处理边界：什么在本机、什么上云>
测试账号：手机号 <号码>，PIN <PIN>；首次进入点「注册」填上述信息即可。
```

### ⚠️ 不要写这些

| 不要写 | 为什么 |
|---|---|
| 「保证合规」「审核通过」 | 超出功能范围 → 判「与实际功能不符」(1.2.1(2)) |
| 「国家级」「最高级」「第一」 | 广告法禁用词 |
| 模糊的功能描述（"提升体验"） | 简介/描述被要求「明确介绍功能点，不能使用模糊词义」 |

## 四、图片预览（提审素材）

**建议传** —— 审核员一眼看懂功能，能降低「功能过于简单」(3.1.5) 的误判风险。

### ⚠️ 一个高频错误：截了**空状态**的页面

**现象**：把「结果页」截了图，但当时没跑过数据 → 全是 0 / 全空。
**审核员看了会以为"没功能"。**

**修法**：
- 截图前**先跑一遍完整流程**让页面有真实数据
- 或者**不传**那张，让审核员用测试账号自己走

### 自动截图

`ms_shots.js` 用官方工具的模拟器截图能力批量截。

**注意参数名**（容易写错）：
- `--path <本地输出路径>`（不是 `--output`）
- `--wait <0-10 秒>` 截图前等待渲染
- `--optimize` **默认 true，写的是 JPEG** → 输出文件扩展名请用 `.jpg`，别用 `.png`（名不符实）

## 五、审核加急

有免费加急额度时（页面显示「剩余 N 次」），**建议用掉**：

- 免费，且**剩余次数不会增值**（不用就一直是 1 次）
- 首次提审最常因**流程性问题**（测试账号、隐私指引）被打回
- **快速出结果 → 当天就能改完重提**，比等几天快得多

**⚠️ 前提**：先把该准备的内容都准备好再提交，别浪费机会。

## 六、提交后

| 结果 | 处理 |
|---|---|
| 通过 | **停在「待发布」** —— 等 ICP 备案下来再点发布（审核通过 ≠ 上线） |
| 被驳回 | 看理由 → 对照下表 |

### 被驳对策表

| 驳回理由 | 真实原因 | 修法 |
|---|---|---|
| 未提供测试账号 | 机制（3.3.4） | 重提 + 填测试账号，**不用改代码** |
| 名称与实际功能不符 | 后台名称 ≠ 小程序内显示 | 核对后台名称审批状态 |
| 隐私指引与实际收集不符 | 声明多了或少了 | 把 `wx.*` 调用全量列出，逐条对照（**两种方向修法相反**） |
| 服务类目与实际功能不符 | 类目选错 | 按功能实质选，详见 [privacy-and-categories.md](privacy-and-categories.md) |
| 功能过于简单（3.1.5） | 只有一页/一个按钮 | 补全功能；并在描述+截图里展示完整链路 |
| 疑似 UGC | 误判 | 回：无评论/留言/发布/分享能力，未接内容安全 API |
| 按钮无响应（3.3.1） | 有死按钮或点了没反应 | 逐个按钮实测 |

### 其他规则

- **同一时间只能有一个审核中的版本**（错误码 `85009`）
- 被驳回后可直接重提，**普通开发者没有次数限制**
- 审核有主观成分，**同样的小程序不同审核员结果可能不同**

## 七、绝对不要做的事

| 不要 | 为什么 |
|---|---|
| 做「审核员看到 A、用户看到 B」 | 违反 5.19 / 5.19.2 |
| 提交未经测试的版本 | 3.3.1/3.3.3 要求可打开、可运行、无严重 Bug |
| 页面里有死按钮 | 3.3.1 明确「按钮没有响应」会被拒 |
| 描述里写超功能的话 | 1.2.1(2) 名称/简介须与实际功能一致 |
| 有账号体系却不做「退出」入口 | 3.5.5 要求有易于发现的退出选项 |
| 自动播放音视频 | 3.5.2 禁止 |
